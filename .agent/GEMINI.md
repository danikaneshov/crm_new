## 1. Концепция и Технологический стек
Мы создаем CRM, где кальянные мастера работают через Telegram Mini App, а владельцы управляют бизнесом через Web Admin Panel.
Система изначально проектируется с поддержкой **множества точек (locations)** — хардкод количества заведений запрещен.

**Стек технологий:**
*   **Frontend (Mini App & Admin Panel):** React / Next.js (или аналогичный современный фреймворк).
*   **Backend:** Node.js (Vercel Functions / отдельный API).
*   **Database:** Firebase Firestore.
*   **Auth (Admin):** Firebase Authentication.
*   **Auth (Masters):** Telegram `initData` (строгая валидация на бэкенде).
*   **Storage (Фото отчетов):** Закрытый Telegram-канал (бот загружает фото туда, в БД хранятся только file_id).
*   **AI / OCR:** Google Gemini API (для парсинга чеков r_keeper).
*   **Deploy:** Vercel (CI/CD через GitHub).

## 2. Архитектура и Безопасность (Критически важно!)

1.  **Frontend ничего не решает:** Фронтенд только отправляет запросы и отображает UI. Все расчеты, валидация прав, определение количества продаж и доступ к точкам происходят **исключительно на backend**.
2.  **Никаких PIN-кодов:** Авторизация мастеров идет через Telegram. Frontend Mini App передает `initData`, бэкенд его криптографически проверяет и сам достает `telegram_id`. Доверять сырому `telegram_id` с фронтенда строго запрещено.
3.  **Изоляция фотографий:** Firebase Storage для фото отчетов **не использовать**. Фотографии отправляются ботом в закрытый Telegram-канал, а в Firestore сохраняются метаданные (`telegram_chat_id`, `telegram_message_id`, `telegram_file_id`).
4.  **Разделение доступов:** Мастер видит в интерфейсе только те точки (locations), которые разрешены ему администратором в Firestore (массив `location_ids`).

## 3. Интеграция AI (Gemini)
Gemini используется для анализа фотографий закрытия смены (чеков r_keeper).
*   **Задача AI:** Распознать конкретные позиции (кальяны и замены). Не нужно заставлять AI считать зарплату.
*   **Формат ответа:** Строго валидный JSON, например: `{"hookahs": 5, "replacements": 4}`.
*   **Валидация:** Бэкенд обязан проверять ответ AI (числа должны быть `>= 0`, аномальные значения отправляются на ручную проверку, статус смены `CORRECTED`).

## 4. Главные бизнес-правила

### Смены и Точки
*   Любая смена строго привязана к `location_id`. Без точки смену открыть нельзя.
*   Мастер выбирает точку на главном экране до открытия смены.

### Распределение работы (Соло / 2 мастера)
*   **Коэффициент смены:** Первый мастер (тот, кто открыл) получает `1.0` смены. Второй мастер получает `0.5` смены.
*   **Формула продаж:** `total_sales = hookahs + replacements`
*   **Распределение при двух мастерах:** 
    *   Второй мастер: `second_sales = Math.floor(total_sales / 2)`
    *   Первый мастер: `first_sales = total_sales - second_sales` (забирает остаток).

### Расчет зарплаты
*   У каждого сотрудника есть `salary_base` (оклад) и `salary_per_sale` (ставка за кальян/замену).
*   **Соло:** `salary_base + (total_sales * salary_per_sale)`
*   **Два мастера:**
    *   Первый: `salary_base + (first_sales * salary_per_sale)`
    *   Второй: `(salary_base / 2) + (second_sales * salary_per_sale)`

### Ревизия
*   Рассчитывается индивидуально на основе отработанных смен с учетом коэффициента (1.0 или 0.5).
*   Формула: `((Должно быть - Фактически) / Общее кол-во смен на точке) * Личные смены мастера`.
